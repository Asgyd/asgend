# Архитектура

- `server.c`: TCP + Unix listener, optional loopback-only HTTP UI, strict request framing, token auth, Host guard and worker pool.
- `db.c`: SQLite/WAL очередь с полем приоритета, aging против starvation, атомарным claim через `BEGIN IMMEDIATE`, idempotency, retries, cancellation, restart recovery и история сессий.
- `orchestrator.c`: отдельная decision-модель/резервный выбор агента, три этапа декомпозиции, критическая проверка, формализация и сбор результатов. Для каждого этапа четыре классификатора ресурсов работают параллельно.
- `agent.c`: prompt из профиля агента и skills/knowledge, ограниченный цикл LLM/tool calling, контекст прошлых сообщений.
- `llm.c` + `net.c`: ограниченный libcurl клиент для OpenAI-compatible Chat Completions и единичная безопасная инициализация libcurl до запуска потоков.
- `models.c`: реестр обычных LLM/decision-моделей и Nodes (local/LAN/Internet), валидация HTTPS для Internet nodes, ленивый/boot-запуск локальных процессов, readiness polling, health/status и остановка process group.
- `config_editor.c`: чтение реальных JSON-файлов, проверка ссылок агент→модель и atomic per-file save для единого дерева `config/`; fingerprint сигнализирует, когда изменения ещё не загружены работающим процессом.
- `tools.c`: allow-listed `echo`, `current_time`, `knowledge_search` и маршрутизация в MCP.
- `mcp.c`: запуск MCP процессов без shell, stdio JSON-RPC, handshake/discovery/call, persistent supervisor с restart/backoff для дочерних stdio-сервисов, остановка process group и OS-level sandbox (rlimits, UID drop, no_new_privs, seccomp, optional/fail-closed Landlock).
- `agents.c` и `config.c`: профили агентов и валидация настроек.

## Жизненный цикл задачи

`queued -> running -> waiting_input -> queued -> running -> completed | completed_without_model | failed | cancelled`. Задача сохраняется в SQLite до ответа о приёме. Рабочие потоки атомарно получают задачи из очереди. Повторная отправка с `idempotency_key` возвращает ранее сохранённую задачу. Временные ошибки повторяются в пределах `runtime.max_retries` с сохранённым в SQLite `next_attempt_at` и backoff 1/2/4/8/16/30 секунд (потолок 30 секунд); stale `running` записи восстанавливаются с учётом счётчика попыток и той же задержки. Операция `dead_letters` показывает терминально упавшие задачи, а `retry_task` возвращает выбранную задачу в очередь ровно на одну дополнительную попытку, сохраняя её историю. При штатном завершении worker-ы не начинают новую работу, невыполненные claims возвращаются в durable-очередь без расходования попытки, а уже начатая работа завершается перед остановкой. Вопрос оркестратора или гибкого агента сохраняется вместе с checkpoint; ответ пользователя повторно ставит ту же задачу в очередь и продолжает с незавершённой подзадачи.

Отмена queued-задания применяется немедленно. Отмена running-задания помечает `cancel_requested` и проверяется оркестратором между подзадачами. Активные HTTP-запросы LLM (OpenAI-compatible streaming и System One JSON) также проверяют флаг через libcurl progress callback и прерываются без ожидания полного `request_timeout_seconds`; task ID передаётся в отдельные потоки параллельной классификации ресурсов. Задержка зависит от частоты вызова progress callback. Синхронный MCP transport пока проверяет отмену на границе вызова, а не внутри ожидания ответа.

Очередь выбирает задачу по `MIN(9, priority + floor(wait_seconds / priority_aging_seconds)) DESC`, затем FIFO по `created_at`. Это позволяет приоритетам работать сразу, но предотвращает бессрочное голодание фоновых задач.

SQLite работает в WAL с `synchronous=FULL`. Это даёт восстановление после перезапуска процесса на одном экземпляре сервера, но не является распределённой очередью для нескольких реплик.

## Декомпозиция и fallback

При включённой LLM этап 1 формирует цель, известные данные, вопросы, предположения и ограничения; этап 2 предлагает шаги; этап 3 исправляет шаги и возвращает оценку качества. Результаты нормализуются перед использованием. При некорректном JSON активируется резервная декомпозиция, а `model_assisted` показывает, прошёл ли данный этап модельную проверку формата. Сервер может приостановить задачу в `waiting_input`. Ответ хранится в истории событий и продолжает ту же задачу с checkpoint; уже завершённые подзадачи не запускаются повторно.

## MCP и безопасность

MCP запускается по заданным `command`/`args` без shell-интерполяции. Перед `exec` окружение дочернего процесса всегда очищается независимо от `sandbox.enabled`; передаются только минимальные безопасные значения и явно заданные строковые пары `mcp.servers[].env` (до 16 на сервер). `PATH`, `HOME`, `TMPDIR` и динамические loader-переменные нельзя переопределить через этот список. Child получает ресурсные лимиты, `PR_SET_NO_NEW_PRIVS`, seccomp запрет сети/опасных syscalls, закрывает не-stderr/stdin/stdout файловые дескрипторы, работает в отдельном временном каталоге, а при EUID 0 сбрасывает UID/GID до nobody. Landlock задаёт allow-list чтения: системные пути для запуска программ, абсолютный путь команды/аргументов, явные `mcp.servers[].read_only_paths` и приватный workspace. Запись/создание/удаление разрешены только внутри workspace. `sandbox.require_landlock=true` заставляет startup MCP завершиться ошибкой, если ядро/контейнер не предоставляет Landlock; при `false` и недоступном Landlock процесс запускается только с остальными ограничениями, и файловая изоляция не гарантирована. Чтение `/usr` и похожих runtime-каталогов разрешено для библиотек/команд; храните там секреты только если готовы раскрыть их MCP процессам. Это не замена контейнеру/VM и отдельному OS-пользователю для враждебного кода. Сервер выполняет `initialize`, `notifications/initialized`, `tools/list` и `tools/call`. После успешного начального handshake supervisor обнаруживает завершение stdio-child и transport-level ошибки записи/чтения, затем запускает новый процесс с exponential backoff 1–30 секунд, повторяя handshake и `tools/list`; это не требует перезапуска ASGEND. Shutdown останавливает supervisor и дожидается его завершения. Каталог alias/schema стабилен для работающих worker-потоков и не мутируется при восстановлении; изменения списка инструментов применяются после перезапуска ASGEND. Первичная ошибка handshake по-прежнему прерывает запуск, а Streamable HTTP endpoint не является дочерним процессом и этим supervisor не перезапускается. Инструменты публикуются модели только если точный alias присутствует в allow-list агента. MCP-процессы всё равно работают с OS-правами службы, поэтому нужны доверенные команды и внешняя изоляция. TCP не шифруется; используйте loopback либо TLS/VPN/SSH перед сетевым развёртыванием. Unix-сокет создаётся как `0600` и проверяет peer UID. Web UI выключена по умолчанию и требует отдельный токен длиной не менее 32 символов.

## Модели и конфигурация

`config/config.json` ссылается на `config/models.json`; профили агентов лежат в `config/agents/*.json`. `agent.model_id` выбирает обычную LLM, а `defaults.decision_model_id` ссылается на `decision_models` и используется для маршрутизации и параллельной классификации ресурсов. Отдельная `defaults.analysis_model_id` либо включённая модель уровня `large` используется для этапов анализа/декомпозиции/финального review; после делегирования управляемый процесс большой модели останавливается перед запуском моделей исполнителей. Агентские профили гибкие, без встроенных специальностей coder/planner/reviewer. `auto_start` означает запуск по требованию, `start_at_boot` — предварительный запуск при инициализации сервера. Процессы запускаются через `execv`, без shell. Configuration editor показывает файлы с диска, валидирует ссылки и сигнализирует `restart_required`, если новые файлы ещё не загружены запущенным сервером. Изменение конфигурации пока требует рестарта; reload без простоя не реализован. Реестр моделей может запускать административно заданный executable, поэтому UI-токен имеет полномочия уровня администратора и должен оставаться секретным.

## Текущие границы

Не реализованы TLS непосредственно в бинарнике, multi-tenant quotas, контейнерная/network namespace изоляция и распределённая очередь. Контекст ограничен по числу сообщений, а не хранится как неограниченный transcript. При выключенной модели статус `completed_without_model` прямо показывает, что фактическое модельное исполнение не производилось.

## Динамический выбор ресурсов

Файловый просмотр CLI использует отдельный `workspace_read_chunk`: ядро открывает путь через `openat`/`O_NOFOLLOW`, читает ограниченный участок через `pread` (не более 64 KiB), возвращает полный размер и следующий byte offset, по возможности выравнивает границы по newline и не допускает разрыва UTF-8 символа. Старые `workspace_read`/`workspace_write` остаются удобным контрактом редактирования с ограничением 1 MiB. TUI загружает следующий/предыдущий фрагмент только на границе прокрутки; навигация мышью использует SGR button-motion, drag selection, вертикальное/горизонтальное колесо и визуально-линейное смещение ленты событий.

`resources.c` сканирует актуальные Markdown-файлы категорий `skills/`, `system_prompts/`, `tools/` и `knowledge/` для каждой подзадачи. Для tools в том же каталоге добавляются описания и схемы реально обнаруженных MCP-инструментов. Четыре инструкции независимы и находятся в `~/.config/asgend/instructions/`: `select_skills.md`, `select_system_prompts.md`, `select_tools.md`, `select_knowledge.md`. При первом запуске отсутствующие инструкции копируются из `instructions/`; сохранённые файлы не перезаписываются.

Каждая категория получает свою динамически заполненную инструкцию с `{{TASK}}`, `{{AGENT}}`, `{{RESOURCE_TYPE}}`, `{{FILES}}`. Четыре вызова выполняются параллельно, большие каталоги разбиваются на последовательные пакеты в рамках соответствующей категории, результаты объединяются по точным идентификаторам файлов. Текущий предел — 512 файлов на одну категорию, максимальная глубина сканирования — 5 каталогов, максимум 48 KiB на отдельный файл; эти пределы защищают память и контекст. Файл, созданный после старта сервера, обнаруживается на следующей подзадаче.

Выбранные skills/system prompts/knowledge попадают в агентскую инструкцию. Выбор tools дополнительно пересекается с `agent.tools`: decision-модель никогда не может выдать сама себе новые права. Если один из пакетных ответов некорректен, категория переключается на fallback к настройкам агента. Метаданные выбранных ресурсов записываются в `formalization[].resource_selection`.

## Nodes и модельные профили

`config/models.json` содержит `nodes`, `models`, `decision_models` и `defaults`. Обычные модели и decision-модель имеют собственные жизненные циклы. `node_id` привязывает профиль к локальному устройству, сети или HTTPS endpoint в Интернете. `enabled` узла обязателен для запуска модели; Internet nodes не принимают HTTP. `local` обозначает управляемые локальные процессы, `localhost` — уже работающий endpoint loopback вроде Ollama. Секреты API задавайте через `api_key_env`, а не храните в репозитории. UI разделяет список задач, чат конкретной задачи, Nodes, профили исполнения и ресурсы. Decision-модель выбирает один гибкий профиль на всю задачу; ресурсы классифицируются независимо для каждого этапа.
