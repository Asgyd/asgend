# Управление локальными моделями

## Единое дерево конфигурации

Сервер и веб-редактор используют одни и те же файлы на диске:

```text
config/
├── config.json        # сервер, пути, TCP/Unix/UI, очередь, MCP и sandbox
├── models.json        # обычные LLM, decision-модели и назначения по умолчанию
└── agents/
    └── generalist.json
```

`paths.models_config` и `paths.agents_dir` связывают файлы в единое активное дерево. Редактор не разрешает менять эти два пути, чтобы не создать ситуацию, где веб-интерфейс пишет в один каталог, а сервер читает другой. Каталоги `skills/` и `knowledge/` содержат содержимое, а не конфигурацию моделей/агентов.

## Реестр моделей: `config/models.json`

Пример верхнего уровня:

```json
{
  "defaults": {
    "model_id": "qwen-coder",
    "decision_model_id": "liquid-d1-3b"
  },
  "nodes": [
    {"id":"local", "name":"Local device (managed processes)", "type":"local", "enabled":true},
    {"id":"localhost", "name":"Localhost inference endpoint", "type":"local", "endpoint":"http://127.0.0.1:11434/v1", "health_url":"http://127.0.0.1:11434/api/tags", "enabled":true},
    {"id":"lan-node", "name":"LAN inference", "type":"lan", "enabled":false, "endpoint":"http://192.168.1.100:8000/v1"},
    {"id":"internet-node", "name":"Remote inference", "type":"internet", "enabled":false, "endpoint":"https://llm.example.com/v1"}
  ],
  "models": [],
  "decision_models": []
}
```

Профили `models` предназначены для агентских ответов и tool calling. Профили `decision_models` используются decision path оркестратора: маршрутизация, классификация ресурсов и распределение этапов. Анализ, первичная декомпозиция и финальное ревью идут через `defaults.analysis_model_id` или доступную включённую модель `tier: "large"`, а не через модель с малой задержкой.

### Поля профиля

| Поле | Значение |
|---|---|
| `id` | Уникальный ID из латиницы, цифр, `_` и `-`; ID должен быть уникален между обоими массивами. |
| `name` | Отображаемое название в UI. |
| `enabled` | Разрешено ли использовать модель. Для демонстрационных профилей по умолчанию `false`. |
| `auto_start` | Ленивый запуск при первом запросе к модели, если процесс ещё не запущен. Не запускает модель, если `enabled` выключен. |
| `start_at_boot` | Запустить модель во время запуска сервера. Если запуск не удаётся, сервер записывает предупреждение и состояние `last_error`, но продолжает запуск с резервной логикой/другими моделями. |
| `executable` | Абсолютный путь к исполняемому файлу для управляемого процесса; пустая строка означает уже работающий внешний inference server. |
| `model_path` | Путь к файлу весов или каталогу, передаваемый как `{model_path}`. Проверяется при включённом автозапуске, если значение задано. |
| `working_directory` | Рабочий каталог дочернего процесса; относительные пути считаются от корня проекта. |
| `args` | Массив аргументов процесса; shell не используется. Подстановки: `{port}`, `{model_path}`, `{model_name}`, `{base_url}`, `{root_dir}`. |
| `port` | Порт, передаваемый процессу; задавайте уникальный порт для каждой управляемой модели. |
| `base_url` | OpenAI-совместимый URL API, обычно оканчивающийся `/v1`. |
| `health_url` | URL readiness-проверки. Если не задан — вычисляется из `base_url`. |
| `model_name` | Имя/идентификатор, передаваемый inference API в поле `model`. |
| `api_key` | Необязательный API key; не используйте его как токен доступа к web UI. |
| `startup_timeout_seconds` | Максимальное время readiness polling. |
| `shutdown_timeout_seconds` | Время ожидания завершения после SIGTERM, затем применяется SIGKILL. |
| `request_timeout_seconds` | HTTP timeout для запросов этой модели. |
| `temperature` | Температура запроса в диапазоне `0..2`. |

Для управляемой модели, если `enabled=true` и включён `auto_start` или `start_at_boot`, `executable` должен быть абсолютным и исполняемым, а `port` — в диапазоне `1..65535`. Если `model_path` задан, файл/каталог должен существовать. Параметры `args` передаются напрямую через `execv`; строки не интерпретируются shell. Менеджер модели создаёт лог в `data/models/<id>.log` с ограниченным доступом.

Если `executable` пустой, профиль описывает внешний сервис (например, Ollama, уже поднятый отдельным менеджером). Сервер не владеет его жизненным циклом и не может гарантировать запуск/остановку внешнего сервиса.

### Привязка моделей к агентам

В `config/agents/generalist.json` хранится гибкий профиль. В нём можно задать предпочитаемую обычную модель, системную инструкцию, skills и allow-list инструментов. Нельзя полагаться на фиксированные встроенные роли `coder`, `planner` или `reviewer`: выбор профиля выполняет decision-модель по возможностям и контексту, а агенты используют общие интерфейсы.

`agent.model_id` имеет приоритет над `defaults.model_id`. Если обе настройки пусты, сохраняется обратная совместимость со старым блоком `local_llm` в `config/config.json`. Если модель выключена/не настроена, задача не притворяется успешным LLM-выполнением — возвращается явный результат `completed_without_model` или используется резервная decision-логика.

`defaults.decision_model_id` должен ссылаться на ID из `decision_models`, а `defaults.model_id` — на ID из `models`. Поле `model_id` агента также должно ссылаться на обычную LLM, не на decision-модель. Редактор проверяет эти связи до записи конфигурации.

## Nodes (локально, LAN, Интернет)

Массив `nodes` хранит точки размещения моделей. Поля: `id`, `name`, `type` (`local`, `lan`, `internet`), `enabled`, `endpoint`, `health_url`, `api_key_env` и необязательное `description`. Модель/decision-профиль указывает `node_id`. Для `local` процесс может быть управляемым через `executable`/`args` или уже работающим локальным endpoint. Для `lan` и `internet` `endpoint` подменяет `base_url` модели: узел LAN разрешает `http://` или `https://`, узел Интернет требует `https://`. Нельзя включить модель, если её узел отсутствует или выключен.

Не публикуйте API-key в конфигурации. Рекомендуемый режим — `api_key_env: "ASGEND_REMOTE_LLM_API_KEY"` и экспорт секрета в окружении службы. Веб-интерфейс содержит вкладки задач и их чат, Nodes, профили исполнения и ресурсы; в Nodes находятся реестр точек и модели, с кнопками включения/выключения профиля и запуска/остановки управляемого процесса.

## Отдельная decision-модель и классификация ресурсов

`defaults.decision_model_id` должен указывать на профиль в `decision_models`, а не в `models`. В поставляемом примере это `liquid-d1-3b` (Liquid AI D1 3B). Путь `/srv/models/liquidai-d1-3b.gguf` — примерная настройка, модель выключена, пока администратор не подтвердит исполняемый файл, реальные веса и параметры запуска.

Для каждого этапа четыре независимые классификации выполняются параллельно на decision-модели. Инструкции хранятся отдельно: `~/.config/asgend/instructions/select_skills.md`, `select_system_prompts.md`, `select_tools.md`, `select_knowledge.md`. При первом запуске отсутствующие шаблоны копируются из `instructions/` проекта, существующие инструкции никогда автоматически не перезаписываются. Они содержат `{{TASK}}`, `{{AGENT}}`, `{{RESOURCE_TYPE}}`, `{{FILES}}`; содержимое `FILES` строится на каждом задании из всех доступных `.md` соответствующей директории и live MCP schemas. Большие каталоги делятся на пакеты, чтобы не превышать контекст модели. `formalization[].resource_selection` показывает итоговые IDs. Выбранный tool по-прежнему должен присутствовать в `agent.tools`, поэтому классификатор не может повысить собственные полномочия.

## Web UI и файловая согласованность

Включите в `config/config.json`:

```json
"ui": {
  "enabled": true,
  "host": "127.0.0.1",
  "port": 8766,
  "auth_token": "<случайный секрет длиной не менее 32 символов>",
  "directory": "ui"
}
```

Откройте `http://127.0.0.1:8766/`. Модельный dashboard отображает доступность и состояние управляемых процессов. Configuration editor редактирует основной JSON, оба массива моделей и все профили агентов. `GET /api/configs` читает дисковые файлы; `PUT /api/configs` проверяет ссылки/форматы, записывает временные файлы и заменяет файлы конфигурации. Если активное содержимое сервера отличается от файлов, интерфейс показывает состояние «нужен перезапуск» и блокирует start/stop модели до перезагрузки процесса. Перезапуск сбрасывает `restart_required`, если активная конфигурация совпадает с диском.

**Редактор конфигурации — административный интерфейс.** Через него можно задать исполняемый файл и аргументы дочернего процесса, который будет запущен с правами ОС-пользователя сервера. Поэтому интерфейс по умолчанию отключён, привязан к loopback и защищён отдельным токеном. Не проксируйте UI напрямую в Интернет и не отдавайте токен недоверенным пользователям. Токены сохраняются в файле настроек, так что сам каталог `config/` должен быть доступен на запись только администратору/службе и иметь резервную копию.

Применение изменений: сохраните файлы → перезапустите `agent-orchestrator` → убедитесь, что UI больше не показывает `restart_required`. В настоящее время конфигурация применяется при запуске процесса; горячее обновление агентского набора и модели без перезапуска намеренно не обещается.

## Запуск, остановка и диагностика

- `start_at_boot=true`: запуск профиля при старте сервера.
- `auto_start=true`: запуск по требованию при первом обращении к соответствующему ID.
- `POST /api/models/llm/<id>/start` и `POST /api/models/llm/<id>/stop`: запуск/остановка управляемой LLM.
- `POST /api/models/decision/<id>/start` и `POST /api/models/decision/<id>/stop`: то же для decision-модели.
- `POST /api/models/{llm|decision}/<id>/enable` и `/disable`: включить/выключить профиль; выключение также останавливает управляемый процесс.
- `GET /api/resources`: каталоги и актуальные IDs `.md` файлов категорий и четырёх инструкций.
- `GET /api/models` или JSON `health`: текущее состояние, URL, PID/статус запуска, ошибки и путь к логу (без вывода API key).

Модельный процесс не считается MCP sandbox-процессом: это доверенный, заданный администратором executable и он работает с правами процесса оркестратора. Для недоверенных бинарников запускайте сервис под выделенным непривилегированным OS-пользователем или используйте отдельный контейнер.


### Семантика узлов и классов моделей

- `local` — модели, для которых ядро запускает локальный executable (например, `llama-server`) и само управляет жизненным циклом процесса.
- `localhost` — endpoint уже запущенного на этом устройстве inference-сервиса, например `http://127.0.0.1:11434/v1` для Ollama. Ядро не запускает его executable, если профиль не содержит команду запуска.
- `lan-node` — доверенный inference-сервис в локальной сети; `internet-node` — удалённый endpoint и только HTTPS. Не публикуйте токены и не отправляйте секретные данные недоверенным endpoint-ам.

Уровни `tier`: `large`/`high` — тяжёлый анализ, декомпозиция и финальный review; `medium` — основное выполнение; `fast` — типовые функции и небольшие исправления; `ultra_fast` — суммаризация/извлечение главного при минимальной задержке; `decision` относится только к отдельному реестру `decision_models`. Текущие максимумы параллелизма: high/large/analysis/decision = 1, medium = 2, fast = 3, ultra-fast = 4–8 в зависимости от числа доступных CPU.

## Динамический планировщик памяти

Для каждой управляемой модели ядро измеряет размер весов на диске и кэширует результат; GGUF metadata (когда читается) используется для оценки KV-cache на токен. Контекст запрашивается автоматически по текущему prompt и tool schemas: целевой размер кэшируется по prompt bucket, а минимальный размер включает расчётный вход плюс запас на ответ. В конфигурации не нужно вручную задавать контекст модели.

Ресурсный план берёт `MemAvailable` и ограничения cgroup, реальный PSS/RSS процессов, свободную/общую VRAM и per-process GPU usage, если драйвер это сообщает. Для shared/UMA модельные веса и KV-cache учитываются в общем пуле RAM, без повторного вычитания как отдельной VRAM. Около 12.5% RAM (с нижней/верхней границей и ограничением относительно размера системы) резервируется для ОС, аллокатора и файлового кэша. Планировщик сначала пытается сохранить максимальный parallel cap по tier и постепенно уменьшает контекст до prompt-safe минимума. Если минимальный план невозможен даже при потенциальном освобождении остальных моделей, запуск отклоняется сразу; если он физически помещается, но сейчас RAM/VRAM заняты, планировщик ждёт освобождения ресурсов до timeout.

Снимок `/api/resources`/`models` показывает `ram_available_mb`, `ram_without_models_estimated_mb`, `running_model_pss_total_mb`, данные по каждому обнаруженному процессу, `disk_size_bytes`, `kv_bytes_per_token_estimate`, `estimated_context_tokens`, `estimated_kv_cache_mb`, `loaded_parallel` и `actual_gpu_memory_mb` (либо `-1`, если per-process GPU usage недоступен). `ram_without_models_estimated_mb` является оценкой (`MemAvailable` плюс PSS известных inference-процессов, с ограничением total/cgroup), а не способом восстановить точно доступную память, которая была бы до запуска моделей. Память удалённого endpoint провайдер должен измерять сам.
